# 第III部 第1章 計算の進化と並列計算

この章は、原稿の第III-1章『計算の進化と並列計算』の React 版です。第III部は、計算資源を増やす方向（Scale Up / Scale Out）と、自動微分というアルゴリズムの方向の二つで、エンタープライズの金融計算を組み立てます。この章では、その第一歩として、一台のコンピュータの中で計算を分けて同時に処理する並列計算を、実際にサーバーで測りながら確かめます。

## III-1.1 金融における情報工学の歩み

1960〜1970年代に Portfolio Theory、CAPM、Black–Scholes／Merton モデルなど現代金融工学の基礎が整い、当時の限られた計算資源で使えるのは解析解を持つモデルが中心でした。1980年代以降、早期行使や経路依存性、複数のリスクファクターを持つ商品が増え、PDE、有限差分、ツリーなどの数値計算が実務に広がります。1990年代にはモンテカルロ・シミュレーションが、複雑なデリバティブの評価と VaR などのリスク管理の基盤になりました。価格は多数のパスの平均

$$
\hat V = \frac{1}{M}\sum_{m=1}^{M} V^{(m)}
$$

として評価され、パスを増やすほど精度は上がる一方、計算量も増えます。

```text
1960s-1970s  Portfolio Theory / CAPM / Analytical Pricing
1980s        PDE / Finite Difference / Tree
1990s        Monte Carlo / VaR / Bump & Revalue
2000s        On-premise Grid / Job Scheduler / Multi-core
2010s        GPU / Cloud / Open Source / Tensor Computing
2020s        Flexible HPC / Massive Monte Carlo / Automatic Differentiation
```

## III-1.2 リーマンショックを経たテクノロジーの潮流

2020年代の変化は、計算資源を「所有する」ことから、必要なときに必要な規模だけ「利用する」方向へ移ったことです。クラウドや HPC のサービスで計算負荷に応じて CPU や GPU を足せるようになり、R や Python を中心とするオープンソースも成熟しました。この二つが重なって、かつては大規模金融機関の専用グリッドでしか現実的でなかった計算を、安く柔軟な環境で実行できるようになっています。

## III-1.3 金融計算におけるハードウェアの限界

計算資源を増やせば一回の評価は速くなります。しかし、リスク感応度を Bump & Revalue（中心差分）

$$
\frac{\partial V}{\partial x} \approx \frac{V(x + h) - V(x - h)}{2h}
$$

で求める限り、リスクファクターごとに評価を繰り返す構造は残ります。

| リスクファクターの数 | 中心差分の評価回数（$2n + 1$） | 自動微分（評価1回と逆向きの計算1回） |
|---|---|---|
| 1 | 3 | 1 + 1 |
| 10 | 21 | 1 + 1 |
| 100 | 201 | 1 + 1 |
| 1,000 | 2,001 | 1 + 1 |

$$
\text{More Cores / More GPUs} \neq \text{Fewer Revaluations}
$$

ハードウェアを増やすだけでは、アルゴリズムが求める再計算の回数は減りません。第III部の後半では、自動微分によって、オプション、金利カーブ、PRDC の多因子リスクへと感応度の計算を広げます。

## III-1.4 並列コンピューティング

金融計算では、入力データを表として持ち、評価関数を各行に当てる形にしておくと、逐次計算から並列計算へ移りやすくなります。原稿は R の `purrr::pmap()` で1行ずつ評価し、同じ関数を `furrr::future_pmap()` に渡して複数のワーカーで評価し、両者が同じ結果になることを確かめています。

```text
Trade / Market / Scenario Data
              |
        Pricing Function
              |
      map()    future_map()
              |
           Result
```

## III-1.5 並列計算を測る

小さすぎるタスクでは、ワーカーの起動やデータの受け渡しのオーバーヘッドが勝って、並列化しても速くなるとは限りません。ここでは、ある程度の計算量を持つ独立したタスクとして、残存約10年の固定利付債を、指定した件数の利回りで評価します。同じ評価をスレッド数を 1、2、4、… と変えて実行し、このサーバーでの時間を測ります。

<TimingPanel />

スレッドを増やしても、評価結果はまったく同じです。各債券の評価は互いに独立なので、どのスレッドがどの行を受け持っても答えは変わりません。速さはスレッド数どおりには伸びず、ある数で頭打ちになります。物理的なコアの数、メモリへのアクセス、スレッドの起動や結果の集約にかかる時間が効くためです。

## III-1.6 並列化の効果と限界

マルチコアによる並列化には明確な限界があります。一台のコンピュータで使える CPU コア、メモリ、GPU には上限があるからです。実務のリスク計算では、数十万件の取引、多数の市場シナリオ、モンテカルロのパス、ストレス・シナリオ、感応度の計算を同時に扱うことがあり、この規模ではタスクを**複数のコンピュータへ配布する仕組み**が必要になります。

$$
\text{Single Machine Parallelism} \longrightarrow \text{Distributed Computing}
$$

## III-1.7 自動微分へ

計算資源を増やして評価を速くしても、感応度を Bump & Revalue で求めるなら、リスクファクターごとに評価を繰り返す構造は残ります。この問題は第III部の後半で自動微分によって扱います。次章では、タスクを複数の計算機へ配布する分散コンピューティングとジョブ・タスクの制御へ進みます。
