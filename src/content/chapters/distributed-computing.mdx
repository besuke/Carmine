# 分散計算

大規模な金融リスク計算やシナリオ評価をジョブに分割し、非同期に処理して結果を集約する分散コンピューティングのアーキテクチャを扱います。シナリオ格子をジョブに割り当てて集約する流れを操作・確認できます。

<PrdcRiskStatus />

<h2 id="jobs">シナリオ格子のジョブ分割・非同期実行と集約</h2>

FX スポット9通り × ボラティリティ5通りの45シナリオをジョブに分割して計算サーバーへ送り、非同期に応答を集約します。1ジョブあたりのシナリオ数と同時送信数を変えて、レーンごとの実行状況とリアルタイム集計を確認できます。

<DistributedPanel />

<h2 id="distributed-jobs">分散コンピューティングの基本構造</h2>

並列計算では、一台のPC上で`future` / `furrr`を利用する並列計算を実装した。そこで使える計算資源は、あくまで一台のMachineに搭載されたCPU CoreとMemoryの範囲に限られる。

実務のRisk Calculationでは、Trade、Scenario、Monte Carlo Pathを多数の独立Taskへ分割し、それらを複数の計算資源へ配布する必要がある。ここでは、PC内のParallel Computingから一段進み、**Task生成 → Job Queue → Scheduler → Worker → Result Aggregation**という分散コンピューティングの基本構造をRで表現する。

```text
Input Data
    |
    v
Task Generation
    |
    v
Job Queue
    |
    v
Scheduler
    |
 +--+--+--+
 |  |  |  |
 W1 W2 W3 W4
 |  |  |  |
 +--+--+--+
    |
    v
Result Aggregation
```

calculate_task_result_LFL <- function(task_ID, input_value, worker_group) {
  tibble(
    task_ID = task_ID,
    worker_group = worker_group,
    input_value = input_value,
    output_value = sqrt(input_value)
  )
}

### 計算資源の統合

ここでは、一台のMachine内部の並列化から、複数の計算資源を前提とする分散処理へ考え方を拡張した。重要なのは、計算関数そのものよりも、TaskをJobとして管理し、Queueへ投入し、SchedulerがWorkerへ配布し、結果を再び集約するというControl Planeである。

この構造があれば、Workerの実体はLocal Process、別Server、Container、Cloud Batch、HPC Clusterへ置き換えることができる。続いて、この計算基盤の上にTrade Data、Market Data、Calibration、Scenario、Pricing、Risk Aggregationを統合し、エンタープライズ金融計算システムとして組み立てる。

<h2 id="enterprise-computing">金融計算アーキテクチャ</h2>

ここまでLocal Parallel Computingと、Job / Task Controlを含むDistributed Computingを扱った。ここでは、それらを実際の金融リスク計算システムの形へ統合する。

エンタープライズ金融計算では、Pricing Functionだけがシステムなのではない。Trade Data、Market Data、Calibration Data、Scenario、Calculation Configurationを分離して管理し、それらをTaskへ変換し、並列・分散実行し、最終的にRisk Tableへ集約する必要がある。

本章ではPRDCを例に、**Data → Scenario → Task → Pricing → Risk → Output**という一連のPipelineをRで構築する。

```text
Trade Data
Market Data
Calibration Data
        |
        v
Scenario Grid
        |
        v
Job / Task
        |
        v
Pricing Function
        |
        v
Risk Table
        |
        v
Aggregation / Report
```

### プライシング・エンジン

ここでは計算基盤に焦点を当てるため、Scenario Pricing Functionは軽量な代理モデルとして表現する。本格的なPRDC Pricing Functionへ置き換えても、Task生成と並列実行の構造は変わらない。

```r

price_prdc_scenario_LFL <- function(
    trade,
    fx_spot,
    fx_volatility,
    domestic_rate,
    foreign_rate
) {
  horizon <- trade$maturity_years[[1]]

  fx_forward <- fx_spot *
    exp((domestic_rate - foreign_rate) * horizon)

  volatility_adjustment <- exp(
    0.5 * fx_volatility^2 * horizon
  )

  tibble(
    trade_ID = trade$trade_ID[[1]],
    fx_spot = fx_spot,
    fx_volatility = fx_volatility,
    domestic_rate = domestic_rate,
    foreign_rate = foreign_rate,
    prdc_proxy_npv = trade$notional[[1]] *
      fx_forward / fx_spot *
      volatility_adjustment
  )
}
```

### エンタープライズ金融計算

ここまでの並列・分散計算は、Pricingを多数回実行することでリスクを求める設計である。計算資源を増やせば処理時間を短縮できるが、Risk Factorが増えるほどBump & RevalueのPricing回数が増えるという構造そのものは残る。

```text
Hardware Acceleration
        |
        v
More Workers / More Cores
        |
        v
Faster Revaluation
        |
        v
But still many Revaluations
```

ここまでで、「計算を分割し、より多くの計算資源で処理する」構造が完成した。しかし、計算資源を増やしても、SensitivityのためにPricingそのものを繰り返す構造は残る。

自動微分では発想を変え、Pricing Programそのものを微分可能なComputational Graphとして構築するAutomatic Differentiationへ進む。ここが、**Hardware / Infrastructure AccelerationからAlgorithmic Accelerationへの転換点**である。
